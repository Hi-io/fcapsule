FCAPSule Development History and Current Product Context
=========================================================

Document purpose
----------------

This document records how FCAPSule developed from its original evidence-capsule idea
through Prototype 1 (P1), the visual/demo experiments, the move toward a final product,
and the present operator-focused state. It is intentionally more narrative than the
repository's architecture and requirements documents. Its purpose is to preserve the
reasoning behind the project: what was attempted, what was learned, what changed after
review, what the current implementation actually does, and which parts remain future
deployment work.

The product documentation in the repository describes the current contract. This file
adds the development story and explains why some earlier ideas, especially model
comparison and reduction metrics, are no longer prominent in the end-user workflow.


1. Initial Brief and Founding Problem
------------------------------------

FCAPSule began with a practical observability problem rather than a desire to build a
general-purpose AI summary tool. Production systems can create very large volumes of
logs, metrics, alerts, topology data, and traces during an incident. Different sources
often retain that data for different, and sometimes short, periods. By the time an
engineer understands that an incident is serious, the raw evidence needed to explain it
may be hard to query, too expensive to retain, or already gone.

The initial product question was therefore:

    Can a system capture the most valuable, cross-domain investigation evidence around
    an alert, reduce it to a durable and inspectable capsule, and help an engineer act
    before ephemeral source data expires?

The key idea was never to replace Prometheus, OpenSearch, Alertmanager, Kafka, tracing,
or a cloud platform. FCAPSule is meant to sit alongside those systems. It observes a
bounded incident window, retains a compact derived record, keeps pointers to source
systems where possible, and gives responders a structured basis for investigation.

The original stable objective can be summarized as follows:

    Preserve the strongest cross-domain investigation evidence while reducing the
    volume, token cost, and retention burden of raw telemetry.

Several boundaries were established early and remain important:

* FCAPSule is not a raw telemetry warehouse.
* It should not store raw distributed traces as a default behavior.
* It should not claim a final root cause without sufficient evidence.
* It should not autonomously remediate production systems.
* Any model call should receive curated evidence, not unrestricted production logs.
* Evidence must remain inspectable even when an AI provider is unavailable.


2. Early Concept Separation: Stable Goal Versus Changeable Design
------------------------------------------------------------------

At the beginning, the project documentation was deliberately separated into two kinds
of material. The stable concept described what FCAPSule was trying to achieve and the
operational problem it addressed. The implementation proposal described possible data
schemas, components, model prompts, UI layouts, and storage choices.

That separation mattered because the goal was stable while the technical design was
expected to change. The team could be confident that FCAPSule should preserve incident
context and support troubleshooting, while still debating how evidence should be scored,
how schemas should evolve, what model should be used, and how the UI should present
results. The project deliberately avoided treating an early schema as a permanent
product promise.

This distinction remained useful later. As P1 became more complete, some early design
ideas were kept, some were moved into offline evaluation, and some were redesigned after
operator-focused review. The core problem statement did not change.


3. Prototype 1: Building the Evidence Pipeline
------------------------------------------------

P1 was the first working technical proof. Its purpose was to establish that FCAPSule
could ingest a bounded case, identify evidence across different operational domains,
produce a compact capsule, and verify that the result retained useful investigation
signals.

The early implementation introduced a normalized incident-case contract. A case
contains metadata, FM alerts, Prometheus-compatible metric series, OpenSearch-compatible
logs, and optional supporting notes. The pipeline validates this material before it
performs any analysis. This was important because an unreliable input contract would
make later reasoning or model output difficult to trust.

The main P1 processing sequence became:

1. Load and validate the case files.
2. Resolve service, namespace, cluster, pod, and dependency identities across sources.
3. Reduce repetitive application logs into masked templates.
4. Analyze time-series metrics against a baseline window.
5. Build an alert-centered incident timeline.
6. Score candidates from each domain using explicit components.
7. Select a compact, balanced evidence set.
8. Generate deterministic investigation hypotheses.
9. Verify that the hypotheses cite real selected evidence IDs.
10. Write capsule, evidence, baseline, and evaluation artifacts.

The important achievement in P1 was not simply producing a shorter text report. It was
the ability to retain an evidence trail. Every selected item has an evidence ID, domain,
source identifier, reason for selection, linked entities, timestamp range, and scoring
components. Hypotheses cite these IDs and remain probabilistic. The system records what
is still missing instead of presenting a confident but unsupported diagnosis.


4. Making Telemetry Domains Explicit
-------------------------------------

One of the earliest critiques of the project was that the difference between domains
was not obvious enough. It was technically correct to say that logs, fault events, and
time series have different structures, but this needed to be visible to a reader who
might otherwise think only in terms of text, images, audio, or generic data types.

The project therefore made the operational domains explicit in both the data model and
the documentation:

* Fault Management (FM): discrete alerts and fault events. These define severity,
  trigger time, affected scope, and fault sequence.
* Performance Management (PM): numerical measurements over time. These support baseline
  comparison, anomaly detection, trend analysis, and capacity/saturation reasoning.
* Application logs: semi-structured text events. These are anonymized, grouped into
  recurring templates, counted, and represented by a small number of examples.
* Topology and configuration: relationships between services, dependencies, pods,
  namespaces, clusters, and configuration changes.
* On-demand traces: temporary request-level context that may be retrievable from a
  source buffer but is not copied into FCAPSule by default.
* AI reasoning: structured, constrained derived text that must cite evidence and state
  uncertainty.

This distinction is central to FCAPSule. The domains are not merely different file
formats. They have different operational meanings, retention properties, and analysis
methods. FM tells a responder that something crossed a threshold. PM shows how behavior
changed. Logs provide detailed patterns. Topology provides scope and dependency context.
Traces may provide the highest-resolution causal data but often have the shortest useful
retention window.


5. The P1 Reference Scenario
----------------------------

To make the project credible, P1 did not use a trivial HTTP 500 example. A more complex,
locally runnable checkout scenario was built. It simulates a small multi-service
application with a checkout service, an inventory dependency, a reservation database
pressure path, structured logs, PM metrics, alert generation, and temporary trace
availability.

The scenario deliberately creates an investigation challenge rather than a single
obvious answer:

* A runtime configuration change is recorded.
* Inventory partition lock contention begins.
* Reservation work starts waiting for database-pool capacity.
* Checkout requests retry inventory calls while the circuit breaker remains closed.
* Retry amplification increases work on the dependency.
* Inventory pool saturation and slow query behavior appear.
* Checkout latency and error rate rise.
* A three-alert FM sequence confirms escalating impact.
* Trace-source access is verified for a limited period, but raw spans are not retained
  by FCAPSule.

The intended evidence-backed path is not stated as a final root cause. It is framed as
an investigation path: lock contention may create dependency latency; retries may
amplify work; pool saturation may sustain the checkout failure. Database diagnostics and
failed-request traces are still required to confirm the causal chain.

This scenario later became the foundation for UI testing, control-plane testing, archive
testing, and real LLM briefing tests. It produced meaningful cross-domain signals rather
than relying on a prewritten error string.


6. P1 Evaluation and the First LLM Experiments
----------------------------------------------

P1 included engineering evaluation work. It measured raw log volume, selected log lines,
template reduction, estimated token reduction, signal preservation, grounding of
hypothesis citations, runtime, retained artifact size, and retention completeness. These
metrics were useful for answering questions such as:

* Did reduction remove the important signals?
* Does the selected evidence still contain the alert, retry, error, latency, saturation,
  and log patterns that an investigation requires?
* Are generated hypotheses grounded in actual evidence IDs?
* How much smaller is a capsule than the original raw telemetry window?

At this stage the project also compared two DeepSeek models, `deepseek-v4-flash` and
`deepseek-v4-pro`, using the same evidence capsule and the same prompt. This was a fair
model-evaluation design: each model received identical input; output quality could be
scored by JSON validity, citation validity, domain coverage, expected signal coverage,
actionability, evidence breadth, cautious causal language, latency, and token use.

The comparison work served its intended purpose: it explored whether a more capable
model generated more grounded, useful investigation reasoning from the same curated
input. The results and prompt were retained as development and evaluation artifacts.

However, later product review made an important distinction. Comparing models is useful
for selecting a model and for writing a research or evaluation report. It is not useful
as the main screen for an SRE responding to an incident. An operator does not need to
decide whether Flash or Pro won a rubric. They need to know what failed, what supports
the likely path, what to do now, and which evidence will disappear.


7. First Visual Layer and Live P1 Demo
--------------------------------------

The project next added a browser-based visual layer. The initial objective was to make
the P1 demo understandable: start from an empty view, generate a failure, show log and
alert activity, build a capsule, run model comparison, and show recorded results.

This led to several iterations:

* A local `.env` mechanism was added for the DeepSeek key, with `.env` ignored by Git.
* A UI was created so a user could start a scenario and watch it progress instead of
  receiving only command-line output.
* The simulation and capsule stages were separated so the user could first see a real
  failure and alert sequence, then run FCAPSule's main evidence process.
* Progress was made visible through stages such as services, baseline, fault injection,
  alert capture, and capsule construction.
* The interface was refined to be more professional and less like an AI-generated
  dashboard of rounded cards and generic explanatory text.

The live P1 UI was valuable for demonstrations. It made it possible to show an actual
process rather than presenting precomputed data. It also exposed design problems that
were less obvious in CLI output: too much information appeared at once, labels lacked
operator context, and development metrics competed with incident understanding.


8. Transition from P1 Demo to a Product-Oriented Control Plane
---------------------------------------------------------------

The next major transition was from a P1 demonstration tool to the beginning of a
product-shaped control plane. The project added persistent state using SQLite and a
local HTTP service. Instead of dealing only with a single generated case, FCAPSule could
track multiple applications, multiple incidents, and multiple capsules.

The local control plane records:

* Application registrations, names, namespace, cluster, environment, and source
  configuration.
* Whether FM, PM, logs, and trace access are configured or available.
* Incident identity, severity, summary, source case location, raw volume observed, and
  trace availability information.
* Capsule identity, location, archive path, retained size, selected evidence count, and
  engineering evaluation fields.

The UI evolved into two views:

1. Operations: a working area for applications, incidents, and retained reports.
2. Incident Lab: a controlled local simulator for development, regression testing, and
   demos.

The Incident Lab is intentionally retained for convenience in the local project today.
It is not considered part of the future production operator product. In a deployed
architecture, collectors and the Operations console should work independently of the
simulator. The Lab can later be extracted into a separate demo/test package.


9. The Main Product Reassessment
--------------------------------

The most important design change came after a direct user-centered critique of the
first product dashboard. The criticism was that the screen still behaved like a
demonstration of FCAPSule's capabilities rather than a useful operational tool.

The visible emphasis on log reduction, signal preservation, model comparison, tokens,
and pipeline quality did demonstrate technical work, but it did not help an SRE make a
decision during an incident. Showing two LLM outputs in the product was especially
misaligned: once a team has selected the best model through evaluation, operators should
not be asked to compare models every time something fails.

The product was therefore reviewed from three roles:

On-call SRE:
    Needs severity, affected application/service, scope, time, user impact, likely
    investigation path, urgent evidence-preservation actions, and concise follow-up.

Application engineer:
    Needs to see whether symptoms connect to a downstream dependency, configuration,
    retry policy, log pattern, or PM trend. They need details they can inspect, not a
    generic summary.

Platform owner:
    Needs to know which applications are protected, which sources are connected, which
    evidence domains were captured, whether traces remain queryable, and whether a
    portable incident artifact can be handed to another team.

The resulting product principle became:

    FCAPSule is an incident-evidence product, not an AI benchmark dashboard.

This was more than a visual redesign. It changed what counts as primary information.
Engineering metrics still exist, but they are now collapsed under diagnostics or kept in
offline evaluation artifacts. The main workflow is an incident queue and an
operator-facing report.


10. Operator-First Incident Reports
------------------------------------

The Operations console was rebuilt around an incident queue. Each row shows severity,
incident summary, registered application, start time, and captured context. The context
is explicitly described as captured context rather than observed impact because counts
such as “three FM alerts, 2,320 logs captured, and 21 PM series” describe what was
available to FCAPSule, not the business or service impact itself.

Opening an incident report now expands it directly beneath the selected row. This was
chosen after feedback that rendering a report below the entire incident table forced
the user to lose context and scroll away from the incident that was clicked. The
in-place expansion resembles message or record inspection in operational tools and
makes selection, comparison, and closing more natural.

The report is organized as follows:

* Incident header: severity, registered service/application, cluster, namespace,
  start time, human-readable title, and summary.
* Observed impact: translated PM metrics rather than raw metric names. Each item states
  the measured peak, normal comparison, owning component, and what the metric means.
* FCAPSule assessment: a deterministic, evidence-grounded investigation path with
  confidence and clear uncertainty. It is explicitly not a final root-cause claim.
* AI incident briefing: an optional, cited DeepSeek Pro second reading, discussed in a
  later section.
* Fault management: alert records shown as FM alerts, with timestamps, descriptions,
  severity, and affected service context.
* Performance management: selected PM series shown as small trend lines, with normal
  and peak values. A red marker identifies the observed peak.
* Log evidence: expandable, anonymized log patterns with matching counts, time range,
  evidence ID, and retained representative lines.
* Incident sequence: ordered alert/timeline events and the dependency path.
* Recommended follow-up: an ordered list with the retention-critical trace action
  placed first.
* Trace availability: clear source-window information and an explicit statement that
  FCAPSule does not retain raw spans.
* Incident package: direct download links for report JSON and the portable capsule ZIP.
* Coverage and engineering diagnostics: source/domain coverage remains visible; reduction
  and validation metrics stay collapsed for maintainers.

This report structure answers a responder's questions in operational order. It does not
require the user to infer what “checkout errors 27” means. For example:

* “Checkout API failure rate” explains that it is the share of checkout API requests
  that failed during the peak interval.
* “Checkout API p95 response time” explains that 95% of checkout requests completed
  within the displayed time during that interval.
* Counter-style metrics describe their values as a collection-interval observation,
  rather than falsely implying they are a complete incident total.
* “Inventory attempts per checkout” explains retry amplification in business terms.
* “Inventory database pool usage” explains saturation as the share of available
  connections in use.

The report is also honest about what it cannot know. In the current simulation, CPU and
memory series are not supplied. The report states that these inputs were not received
and that host-level pressure cannot be ruled out. It does not show green/zero values or
claim that CPU/memory were unaffected.


11. How FM, PM, and Logs Are Used Together
-------------------------------------------

The product now makes the cross-domain reasoning path observable instead of asking a
user to trust a summary.

FM contribution:
    FM establishes when the incident became actionable and which thresholds or service
    conditions fired. In the reference scenario, the sequence includes retry
    amplification, inventory pool saturation, and checkout error-budget burn.

PM contribution:
    PM provides the behavior over time. The report includes error rate, API p95 response
    time, inventory attempts per checkout, and inventory database pool utilization. The
    charted signals show the ordinary/typical baseline and incident peak so the responder
    can see a change, rather than reading an anomaly score.

Log contribution:
    Log patterns show the concrete text behavior behind the hypothesis without copying
    every raw log. Examples include reservation database pool exhaustion, inventory
    reservation attempts failing while the breaker is closed, checkout aborts after
    retry budget exhaustion, and reservation query deadlines with partition/lock waits.
    The user can expand a pattern to inspect representative anonymized lines.

Topology contribution:
    The report displays the dependency path, for example edge gateway to checkout API,
    checkout API to inventory API, and inventory API to reservation database. This puts
    the PM and log observations into a service/dependency context.

Trace contribution:
    Trace access is treated as a retention-sensitive source action. FCAPSule records
    whether traces can still be queried from the source, the available window, and the
    fact that raw spans are not retained in the capsule. It does not pretend that a
    trace query was completed when only source availability was verified.


12. LLM Strategy: From Comparison to Grounded Optional Briefing
----------------------------------------------------------------

The project's LLM design changed in response to both product review and real provider
behavior.

The first model strategy was comparison. Flash and Pro were both called over the same
capsule so quality, latency, citations, and coverage could be measured. This remains a
valid offline evaluation workflow and can still be used to compare providers or models.
It is documented separately because it is valuable for maintainers and research.

For the product, two facts became clear:

1. A model provider must not delay a responder's access to retained evidence.
2. A visible model race is not a useful incident-response UI.

An earlier live provider experiment took approximately 89 seconds and returned
incomplete structured output for a large comparison prompt. That was an important
finding, not merely a failure. It showed why the primary report must be deterministic,
fast, and available without an LLM.

The current product strategy is therefore layered:

Layer 1: deterministic report
    The pipeline selects and verifies evidence, builds hypotheses, records uncertainty,
    generates the report, and creates the archive without a provider call.

Layer 2: optional AI incident briefing
    After a report exists, the user may request a DeepSeek Pro briefing. The briefing
    receives a deliberately compact input: incident identity, deterministic assessment,
    uncertainty, selected FM alerts, selected PM signals, selected log patterns, and
    recommended actions. It does not receive unbounded raw logs or full provider
    transcripts.

Layer 3: validation gate
    The model must return a strict JSON object containing an operator brief, first
    action, reason for that action, evidence IDs, and uncertainty. It must cite two to
    five evidence IDs that already exist in the retained report. A response with invalid
    JSON, unknown citations, missing fields, or missing uncertainty is rejected.

Layer 4: retention boundary
    A successful briefing is stored as `ai_briefing.json` and included in the derived
    archive. Provider prompts and transcripts are not archived. If the provider is
    unavailable, slow, malformed, or rejected, the deterministic report remains usable.

This arrangement gives the LLM a concrete role: it can prioritize and phrase a concise
investigation briefing from curated cross-domain evidence. It cannot silently invent a
root cause or prevent a responder from accessing the actual evidence.

The latest real test used DeepSeek Pro with the checkout incident. A first narrow request
using too small an output budget was correctly rejected because the model produced no
usable final JSON. The implementation was then adjusted to allow reasoning-capable
models enough token budget to emit their constrained final object. A subsequent call
completed in approximately 19.5 seconds and passed validation. It cited retained
pool-exhaustion, deadline, and retry log evidence and selected failed-request trace
retrieval as the first action. This result is meaningful because the model output was
checked against the report rather than simply displayed.


13. Real Verification Data and Results
--------------------------------------

The project has been tested with actual local simulation runs, not static mock results.
One verified `orders-checkout` scenario produced:

* 1,694 structured logs.
* 21 metric series.
* Three FM alerts.
* A 51.7% checkout error rate.
* 20 checkout errors in the relevant sampled observation.
* 142 ms p95 checkout latency compared with a 22 ms baseline.
* A 2.06x retry factor compared with a normal 1.00x.
* Inventory pool pressure.
* A verified 900-second source trace retrieval window.

The deterministic capsule and report for this scenario were generated in approximately
0.04 seconds, without waiting for a model provider. The ZIP archive was verified to
contain the derived artifacts and to exclude raw telemetry and LLM prompt material.

A later `checkout-platform` simulation used in the latest UI verification produced:

* 2,320 structured logs.
* 21 PM series.
* Three FM alerts.
* 48.3% checkout API failure rate at the peak interval.
* 27 failed checkout API requests in the peak collection interval versus a typical zero.
* 137 ms checkout API p95 response time versus a 17 ms normal value.
* 2.02 inventory attempts per checkout versus a normal 1.00.
* 100% inventory database pool usage versus an 87.5% normal baseline.
* 57 pool-exhaustion observations in the peak interval.

The latest report archive for this scenario contains:

* `capsule.md`
* `capsule.json`
* `evidence.json`
* `evaluation.json`
* `baselines.json`
* `incident_report.json`
* `ai_briefing.json` when a valid briefing has been requested
* `dashboard.html` as a retained development/evaluation surface

It does not contain raw logs, complete raw metric exports, raw trace spans, API keys,
provider prompts, or LLM transcripts.


14. Testing and Quality Controls
--------------------------------

FCAPSule currently uses dependency-light Python tests and runs its local web app through
the standard library HTTP server. The automated suite covers validation, log reduction,
anonymization, metric analysis, entity resolution, evidence selection, hypothesis
grounding, case loading, archive boundaries, incident-lab simulation, control-plane
persistence, HTTP routes, model-comparison scoring, and the AI briefing validation
contract.

The latest full verification run completed with 27 passing automated tests.

Beyond automated tests, the following behavior has been manually checked in the local
browser UI:

* The Operations page loads existing persisted applications and incident history.
* Opening a queue row expands the correct report underneath that row.
* The report can be closed without losing the rest of the queue context.
* FM, PM, log, trace, package, and coverage sections are distinct and readable.
* PM charts render as non-empty SVG trend lines with normal and peak values.
* Log patterns are presented as expandable evidence instead of a generic opaque list.
* The report no longer re-renders every second while a user is reading it idle.
* During simulation and capsule work, the Lab continues to update progress live.
* The report JSON and capsule archive links resolve through the local artifact route.
* The deterministic report exists before optional LLM enrichment.
* A live DeepSeek Pro briefing is retained only after passing evidence-citation checks.


15. Current Architecture
------------------------

The current local architecture has the following components:

Incident Lab
    A controlled local multi-service failure generator. It makes baseline and incident
    traffic, triggers lock contention/retry behavior, emits FM alerts, writes normalized
    case files, and verifies source trace availability. It is development/demo tooling.

Case loader and schemas
    Validate case files, timestamps, alerts, PM series, and logs before processing.

Processing pipeline
    Performs log anonymization/template reduction, PM anomaly analysis, entity
    resolution, alert timeline construction, evidence scoring and selection, deterministic
    hypothesis generation, and citation verification.

Incident report projection
    Converts the retained capsule into responder-facing concepts: translated impact,
    FM records, PM signals, log patterns, actions, coverage, trace retention, and
    diagnostics. This keeps the UI from depending directly on internal scoring shapes.

Control plane
    Uses SQLite to store applications, incidents, and capsules. It coordinates background
    simulation and capsule jobs and exposes state through local HTTP API endpoints.

Operations UI
    Displays the incident queue, in-place reports, application coverage, artifact
    downloads, and optional validated AI briefing.

Optional AI briefing module
    Calls DeepSeek Pro only after a report exists, validates the structured response,
    and stores a compact cited briefing when accepted.

Archive writer
    Creates a portable derived-only ZIP. The archive intentionally does not duplicate
    raw source telemetry.

The intended future deployment replaces local case files and the simulator with
read-only adapters or collectors for real alert, metric, log, topology, and trace
systems. The incident contract, retention boundary, evidence logic, report projection,
and operator experience should remain consistent.


16. User Feedback and Its Direct Effect on the Product
-------------------------------------------------------

The project has changed through repeated feedback rather than following a fixed initial
UI plan. The major feedback-to-change links are:

Feedback: domains were not obvious enough.
Change: FM, PM, logs, topology, traces, and AI reasoning became explicit data and UI
domains with different labels and roles.

Feedback: the demo should show a real process rather than a completed dashboard.
Change: Incident Lab was built with an empty initial state, real local fault generation,
separate simulation/capsule actions, progress phases, alerts, logs, and live updates.

Feedback: the simulation should be harder than a simple endpoint error.
Change: a multi-service inventory lock-contention/retry-amplification/pool-saturation
scenario was created.

Feedback: comparing Flash and Pro was useful for evaluation but not for final users.
Change: model comparison was removed from the primary operations workflow and retained
as an offline evaluation capability.

Feedback: the UI should look less like a generic AI dashboard.
Change: the interface moved toward an operational workspace: dense tables, restrained
styling, direct controls, in-place records, and fewer rounded cards or explanatory
marketing phrases.

Feedback: raw reduction metrics did not help an SRE understand an incident.
Change: compression, signal preservation, grounding, runtime, token, and model
statistics were moved into collapsed engineering diagnostics and offline artifacts.

Feedback: a report should appear near the item that was selected.
Change: reports now expand immediately beneath the matching incident queue row.

Feedback: “supporting evidence” was too abstract, impact labels were hard to interpret,
and the source of a conclusion was unclear.
Change: evidence is now separated into FM alert records, PM trend lines, and expandable
anonymized log patterns; impact values explain their meaning and normal comparison.

Feedback: users need to know where a capsule is kept and whether it can be exported.
Change: the report exposes direct downloads for the JSON report and portable archive.

Feedback: AI should add a positive, practical contribution instead of simply displaying
another generic summary.
Change: a narrowly scoped, optional, citation-validated AI briefing was added. It
prioritizes an investigation action from retained evidence and cannot replace the
deterministic report.

Feedback: the Lab is useful now but should not become part of the final deployed product.
Change: the current documents classify the Lab as temporary local demo/regression tooling
that can later be extracted from the Operations product.


17. What Is Deliberately Not Yet Claimed
----------------------------------------

FCAPSule is not yet a distributed production deployment. The current local project is a
reference implementation and a product-shaped prototype with real local behavior. It
does not yet provide:

* Live authenticated collectors against a real Kubernetes cluster, Prometheus,
  OpenSearch, Alertmanager, or tracing backend.
* A real source-system deep link for every retained evidence item.
* Incident acknowledgement, assignment, escalation, paging, or ticketing integration.
* Multi-tenant access control, RBAC, audit log policy, encryption-at-rest policy, or
  formal data-governance integration.
* Distributed worker queues, back-pressure controls, replicated storage, or high
  availability.
* Automatic remediation.
* A guarantee that an LLM can identify the final root cause.

The product is also deliberately cautious about source coverage. If CPU, memory,
database diagnostics, Kafka lag, or other signals have not been connected, the report
should name those as unknown rather than infer a negative result from missing data.


18. Current User Workflow
-------------------------

For local use today:

1. Start the local FCAPSule server with the CLI serve command.
2. Open the Operations console.
3. For a demo or regression case, open Incident Lab, configure the local application
   name/ID and request load, then run the simulation.
4. Watch the baseline, injection, FM alert, and capture stages.
5. Build the capsule after the incident is captured.
6. Return to Operations. The simulated application appears in Application Coverage and
   the incident appears in the queue.
7. Open a report directly inside the queue.
8. Read observed impact, the deterministic assessment, FM alerts, PM trends, log
   patterns, dependency path, trace window, and ordered action list.
9. Download the report or portable capsule where needed.
10. Optionally request the AI incident briefing after reviewing the deterministic
    evidence. Treat it as a cited second reading, not the sole investigation result.

The operations console and capsule pipeline work without the optional provider call.
The local API key resides in `.env`, which is ignored by Git, and is loaded only for
optional DeepSeek functionality.


19. Current State Summary
-------------------------

FCAPSule has progressed from a P1 evidence-pipeline prototype into a local,
operator-oriented incident-evidence product reference implementation.

The strongest current capabilities are:

* Real, reproducible complex incident generation for testing and demos.
* Explicit multi-domain handling for FM, PM, logs, topology, and trace access.
* Log anonymization and compact evidence retention rather than raw duplication.
* Baseline-aware PM anomaly analysis and visible trend inspection.
* Domain-balanced evidence selection with provenance and grounded hypotheses.
* Persistent multi-application, multi-incident local control-plane state.
* An incident queue and in-place responder reports designed around operational actions.
* Clear package export and retention-window handling.
* An optional LLM briefing with strict evidence-citation and uncertainty rules.
* Automated and browser-level verification of the main flows.

The remaining work is primarily integration and deployment work: connect real source
systems, define access/governance policy, add operational ownership workflows, and move
from a local SQLite/in-process service to the chosen distributed runtime when the product
is ready. Those future changes should preserve the central FCAPSule principle: collect
the right investigation context at incident time, keep it compact and inspectable, and
make the next safe action obvious before the source evidence disappears.
